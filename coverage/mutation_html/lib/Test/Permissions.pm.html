  247: =head1 DESCRIPTION
  248: 
  249: Test suites often need to know whether C<chmod> really takes access away,
  250: so they can skip tests that rely on an unreadable file or an unsearchable
  251: directory.  The usual guess, C<skip ... if $E<gt> == 0>, is wrong on:
  252: 
  253: =over 4
  254: 
  255: =item * Windows, where C<chmod> only sets the read-only attribute;
  256: 
  257: =item * C<fakeroot>, and containers where a non-root user holds
  258: C<CAP_DAC_OVERRIDE>;
  259: 
  260: =item * filesystems that ignore mode bits (FAT, some SMB/NFS/FUSE mounts,
  261: Cygwin C<noacl> mounts);
  262: 
  263: =item * root in a user namespace, where root may I<not> be able to bypass
  264: modes.
  265: 
  266: =back
  267: 
  268: Test::Permissions does not guess.  It tries the operation on a scratch
  269: file in the directory you care about, and reports what actually happened.
  270: Results are cached per process.
  271: 
  272: Four kinds of access can be probed:
  273: 
  274: 	Kind     Question                                          Restricted mode
  275: 	read     can a file be made unreadable?                    file 0
  276: 	write    can a file be made unwritable?                    file 0400
  277: 	create   can a directory be made to refuse new files?      directory 0500
  278: 	search   can a directory be made unsearchable (stat of a   directory 0
  279: 	         file inside it fails)?
  280: 
  281: What to expect (your tests must not rely on these; that is the point):
  282: 
  283: 	Environment                        read  write  create  search
  284: 	Linux/BSD/macOS, normal user        1     1      1       1
  285: 	Unix root, or CAP_DAC_OVERRIDE      0     0      0       0
  286: 	Windows (NTFS)                      0     1      0       0
  287: 	FAT or a mount that ignores modes   0     0      0       0
  288: 
  289: =head2 Which directory to probe
  290: 
  291: The answer depends on the filesystem, so pass the directory your fixtures
  292: live in (usually your own C<tempdir>).  If you pass nothing, the probe
  293: runs in C<< File::Spec->tmpdir >>, which may be on a different filesystem
  294: from your fixtures (a C<tmpfs>, for example) and give a different answer.
  295: 
  296: =head2 How a probe works
  297: 
  298: Each probe creates a fresh directory C<P> inside the target directory and
  299: then:
  300: 
  301: =over 4
  302: 
  303: =item 1. B<Setup>: creates the scratch objects with explicit modes, so the
  304: answer does not depend on your C<umask>.
  305: 
  306: =item 2. B<Baseline>: does the operation while it is allowed.  If that
  307: fails, the filesystem cannot tell us anything, and the answer is 0.
  308: 
  309: =item 3. B<Restrict>: C<chmod>s to the restricted mode and checks, with
  310: C<stat>, that the owner's permission bits really changed.  If not (this is
  311: what happens on Windows), the answer is 0.
  312: 
  313: =item 4. B<Attempt>: does the operation again.  It must fail with
  314: C<EACCES> or C<EPERM> for the answer to be 1.
  315: 
  316: =item 5. B<Restore and clean up>: always, even if an earlier step failed.
  317: Nothing is left in the target directory.
  318: 
  319: =back
  320: 
  321: A probe never dies and never warns: anything that goes wrong becomes an
  322: answer of 0, and L</why_not(kind, dir)> tells you why.  Only mistakes in
  323: the call itself (an unknown kind, a directory that does not exist) croak.

 1560: 
 1561: =over 4
