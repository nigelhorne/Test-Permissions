  329: =head1 DESCRIPTION
  330: 
  331: Test suites often need to know whether C<chmod> really takes access away,
  332: so they can skip tests that rely on an unreadable file or an unsearchable
  333: directory.  The usual guess, C<skip ... if $E<gt> == 0>, is wrong on:
  334: 
  335: =over 4
  336: 
  337: =item * Windows, where C<chmod> only sets the read-only attribute;
  338: 
  339: =item * C<fakeroot>, and containers where a non-root user holds
  340: C<CAP_DAC_OVERRIDE>;
  341: 
  342: =item * filesystems that ignore mode bits (FAT, some SMB/NFS/FUSE mounts,
  343: Cygwin C<noacl> mounts);
  344: 
  345: =item * root in a user namespace, where root may I<not> be able to bypass
  346: modes;
  347: 
  348: =item * root on an NFS export with C<root_squash>, where root is treated
  349: as "nobody".
  350: 
  351: =back
  352: 
  353: Test::Permissions does not guess.  It tries the operation on a scratch
  354: file in the directory you care about, and reports what actually happened.
  355: Results are cached per process.
  356: 
  357: Seven kinds of access can be probed:
  358: 
  359: 	Kind     Question                                          Restricted mode
  360: 	read     can a file be made unreadable?                    file 0
  361: 	write    can a file be made unwritable?                    file 0400
  362: 	create   can a directory be made to refuse new files?      directory 0500
  363: 	search   can a directory be made unsearchable (stat of a   directory 0
  364: 	         file inside it fails)?
  365: 	exec     can a script be made unrunnable?                  file 0600
  366: 	delete   can a directory be made to keep its files?        directory 0500
  367: 	sticky   does the sticky bit stop one user deleting        directory 01777
  368: 	         another user's file?
  369: 
  370: What to expect (your tests must not rely on these; that is the point):
  371: 
  372: 	Environment                        read write create search exec delete sticky
  373: 	Linux/BSD/macOS, normal user        1    1     1      1      1    1      0 (a)
  374: 	Unix root, or CAP_DAC_OVERRIDE      0    0     0      0      1(b) 0      1
  375: 	fakeroot                            0    0     0      0      1(b) 0      0
  376: 	Windows (NTFS)                      0    1     0 (c)  0      0    0 (c)  0
  377: 	FAT or a mount that ignores modes   0    0     0      0      0    0      0
  378: 	a noexec mount                      .    .     .      .      0    .      .
  379: 
  380: 	(a) the sticky probe must act as two users, so it needs root
  381: 	(b) even root cannot run a file that has no execute bit at all
  382: 	(c) Windows ignores the read-only attribute on directories
  383: 
  384: =head2 Which directory to probe
  385: 
  386: The answer depends on the filesystem, so pass the directory your fixtures
  387: live in (usually your own C<tempdir>).  If you pass nothing, the probe
  388: runs in C<< File::Spec->tmpdir >>, which may be on a different filesystem
  389: from your fixtures (a C<tmpfs>, for example) and give a different answer.
  390: 
  391: =head2 How a probe works
  392: 
  393: Each probe creates a fresh directory C<P> inside the target directory and
  394: then:
  395: 
  396: =over 4
  397: 
  398: =item 1. B<Setup>: creates the scratch objects with explicit modes, so the
  399: answer does not depend on your C<umask>.
  400: 
  401: =item 2. B<Baseline>: does the operation while it is allowed.  If that
  402: fails, the filesystem cannot tell us anything, and the answer is 0.
  403: 
  404: =item 3. B<Restrict>: C<chmod>s to the restricted mode and checks, with
  405: C<stat>, that the owner's permission bits (for C<sticky>: all the mode
  406: bits) really changed.  If not (this is what happens on Windows), the
  407: answer is 0.
  408: 
  409: =item 4. B<Attempt>: does the operation again.  It must fail with
  410: C<EACCES> or C<EPERM> for the answer to be 1.
  411: 
  412: =item 5. B<Restore and clean up>: always, even if an earlier step failed.
  413: Nothing is left in the target directory.
  414: 
  415: =back
  416: 
  417: A probe never dies and never warns: anything that goes wrong becomes an
  418: answer of 0, and L</why_not(kind, dir)> tells you why.  Only mistakes in
  419: the call itself (an unknown kind, a directory that does not exist) croak.
  420: 
  421: =head2 Paths with non-ASCII characters
  422: 
  423: Directory and file names are used exactly as perl's own file functions
  424: use them: as byte strings.  On Unix, pass the same (usually UTF-8
  425: encoded) bytes you would pass to C<open>.  On Windows, perl's file
  426: functions use the ANSI code page, so a name with characters outside it
  427: cannot be found, and the call croaks with C<error_not_a_directory> or
  428: C<error_no_such_path>.  Names in messages are shown as they are, except
  429: that control and bidirectional-override characters are escaped.
  430: 
  431: =head2 Taint mode
  432: 
  433: The functions work under C<perl -T>.  The directory you pass is checked
  434: with C<-d>, and its canonical path is then untainted, because the probe
  435: only creates its own scratch directory inside it.  C<with_revoked>
  436: likewise untaints the path you give it, because changing its mode is what
  437: you asked for.  The C<exec> probe runs its script with C<PATH>, C<IFS>,
  438: C<CDPATH>, C<ENV> and C<BASH_ENV> removed from the environment.

 2517: =head1 FAILURE POLICY
 2518: 
 2519: =over 4
 2520: 
 2521: =item * B<Caller errors croak>: an unknown kind, a C<dir> that is not an
 2522: existing directory, a C<path> that does not exist, bad arguments
 2523: (reported by Params::Validate::Strict or Params::Get), or an unknown
 2524: message key.  C<with_revoked> also croaks if it cannot change or restore
 2525: the mode it was asked to change.
 2526: 
 2527: =item * B<Probe errors never escape.>  Anything that goes wrong inside a
 2528: probe becomes a 0 answer with a reason.  A helper whose job is to decide
 2529: whether to skip must never be the thing that fails your test file.
 2530: 
 2531: =item * B<No warnings.>  Many suites run under L<Test::Warnings> or C<-W>,
 2532: so a warning would itself fail them.  Use L</why_not(kind, dir)> for
 2533: diagnostics.
 2534: 
 2535: =item * A failed restore or cleanup makes the answer 0, and is added to
 2536: the reason (C<reason_cleanup_failed>).
 2537: 
 2538: =back

 2540: =head1 LIMITATIONS
 2541: 
 2542: =over 4
 2543: 
 2544: =item * Results are per directory (or per device, see
 2545: L</set_cache_scope(scope)>), per effective user and groups, and per
 2546: process.
 2547: 
 2548: =item * A directory whose permissions or mount change after the first
 2549: call keeps its cached answer until L</clear_cache()>.
 2550: 
 2551: =item * Probing needs write access to C<dir>: the probe creates a scratch
 2552: directory there.  Without it the answer is 0 (C<reason_setup_failed>).
 2553: 
 2554: =item * The probes change only mode bits.  L</acl_denies(kind, path)>
 2555: detects an ACL that denies access to an existing path, but no probe
 2556: creates ACLs.
 2557: 
 2558: =item * The mode check after C<chmod> compares the owner's permission
 2559: bits (all bits for C<sticky>), because the probe runs as the owner of its
 2560: scratch files, and because perl on Windows reports a read-only file as
 2561: 0444.
 2562: 
 2563: =item * The C<sticky> probe needs root, and assumes that uids 65533 and
 2564: 65534 can own files.  In a user namespace that maps only one uid (such as
 2565: C<unshare -r>), giving the file away fails and the answer is 0 with
 2566: C<reason_setup_failed>.
 2567: 
 2568: =item * Reasons embed the system's error text in the current locale.
 2569: 
 2570: =item * Needs perl 5.26 or later, because Params::Validate::Strict does.
 2571:
